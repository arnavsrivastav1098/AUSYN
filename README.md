# Ausyn

Ausyn is a native Windows desktop companion built in C++20 with Qt 6. It turns computer health data into clear explanations, cautious predictions, and safe, user-controlled recommendations.

Version 0.5.0 keeps five destinations: **Main dashboard, Performance, Ask Ausyn, Logs, and Settings**. Dashboard resource cards open separate live detail windows; Running apps opens a searchable process window. Ausyn supplies its own title-bar controls and resize handles. Proactive Ausyn popup cards show a finding, its evidence, a next step and a direct review action without a chat question. Settings includes notification channels, quiet hours, sensitivity, background behavior, local learning and exact executable rules. See the [interface guide](docs/ui-guide.md).

The background companion follows a stable foreground task without requiring a Keep button. It offers executable-based activity modes, optional app baselines and recurring-pressure learning, a short RAM-headroom projection, battery session guidance, measured task recaps, an interruption budget with a digest, and a governor for Ausyn's own resource cost. Approved background priority rules can execute without another prompt, then compare fresh readings and undo when relief cannot be measured. A tray briefing, pause, quiet mode and undo work without opening the dashboard. Charts show shaded history, arrival pulses and hover details for actual samples. Live notification updates preserve their size, position and dismissal deadline. See [background companion](docs/background-companion.md) for configuration and limits.

## Install and run

Version 0.4.0 adds the supplied Ausyn icon to Windows, the installer, tray and interface. Its workload companion tracks session-only foreground activity and changing pressure episodes: first observation, continued use, increasing pressure, a different background CPU contributor, and measured recovery. Unchanged conditions do not generate another episode card. Open cards refresh readings without extending their dismissal timer.

**Keep your work moving** lets you choose a running app to preserve in recommendations. **Compare my change** compares the next 30 seconds with the captured baseline. **Review background relief** offers a confirmed, temporary Below Normal CPU priority for one verified background process, with automatic restoration and a Restore button. This does not free RAM or promise performance. Ask Ausyn resolves short local follow-ups and supports separately opted-in recent conversation and cloud reasoning for PC questions.

- **Installer:** run `dist/Ausyn-Setup-0.5.0-Windows-x64.exe` and approve the Windows administrator prompt. Ausyn installs under `C:\Program Files\Ausyn` and registers a standard Windows uninstall entry.
- **Portable:** extract `dist/Ausyn-0.5.0-Windows-x64.zip` to a folder and run `ausyn.exe`.

The release packages include the Qt and Visual C++ runtime files needed to run Ausyn. Build tools are only needed to compile the source. See [installation](docs/installation.md) for first-run, data-location, and uninstall details.

## Build from source

The supported build is 64-bit Windows with Visual Studio 2022 C++ tools, CMake 3.24 or newer, and a Qt 6.6+ MSVC x64 kit containing Concurrent, Core, Gui, Network, Sql, and Widgets. From PowerShell at the project root:

```powershell
.\scripts\build.ps1 -Configuration Release
.\scripts\package.ps1 -Configuration Release
```

Inno Setup 6 is optional for producing the installer; without it, packaging still creates the portable ZIP. See [development](docs/development.md).

## Product boundary

Ausyn is a local-first monitor and written assistant. It does not run a custom antivirus scan, close processes, delete files, install updates, predict an exact hardware-failure date, or speak aloud. It can inspect sleep blockers and offers user-confirmed switching among power plans Windows makes available on the PC, verifies the change, and offers session-only undo. Its optional Windows sign-in setting only adds or removes Ausyn from the current user's startup list. Optional cloud AI is separate, off by default, and requires review and approval for each request. See [blueprint alignment](docs/blueprint-alignment.md) for implemented scope and boundaries.

## Project status

Concurrent CPU and memory pressure across the same analysis window is reported as one combined finding. Recent per-process CPU is described as an association, not proof of cause. Current process readings require process-name sharing and a relevant question; fresh session goals may include app names only with sharing enabled. Recent conversation is a separate opt-in, bounded and previewed before each request.

Event Intelligence also includes a bounded, local incident history view. It shows Ausyn findings as active or resolved, with first-observed and last-activity times plus the stored evidence and recommendation. The list follows the selected local history period and is capped at 250 entries per refresh; no process-level history is added. A resolved state only means the finding rule stopped matching in Ausyn's later observations, not that a particular event or action caused recovery.

The dashboard heads-up is a ranked briefing rather than one long alert paragraph. It turns current findings, near-term memory/battery/storage estimates, security notices, Windows event patterns, and startup-resource signals into cards with the evidence, a cautious next step, and a direct link to the relevant page. The briefing shows the capture time and age of its latest system sample, and flags it as stale after three selected sampling intervals (with a ten-second minimum). Its written readout also refreshes when a sample becomes stale and recovers when fresh data arrives. Categories can be filtered; items can be snoozed for 30 minutes, one hour, four hours, or until tomorrow, or dismissed until that signal clears. These choices persist in local settings and can be restored from the hidden-items view. “Ask Ausyn to explain” opens a written, local-only explanation with the card’s summary, evidence, and next step already in context. The cards are generated locally from existing measurements and scans. Their ranking indicates review priority, not certainty or cause, and does not trigger system changes.

Guided troubleshooting provides symptom-specific evidence views and user-led checklists for slow performance, heat/noisy fans, high memory use, low storage, battery drain, network slowness, application crashes, and game preparation. It labels stale samples, distinguishes missing sensor support from a normal reading, summarizes only the measurements relevant to the selected symptom, and links into the deeper Ausyn page. Checklist progress remains in memory for the current session. A user-requested clipboard summary excludes per-process names. The local Assistant handoff carries the selected evidence directly and stays offline.

The sidebar has five destinations: Main dashboard, Performance, Ask Ausyn, Logs and Settings. Each has a saved Simple/Details switch. Related tools sit within those pages, and specialist tabs appear in Details mode. The dashboard’s system check displays its answer inline. Settings also offers a saved Light appearance; Dark remains the default.

Ausyn leads with a local “Ausyn’s read” on the dashboard. It summarizes the highest-priority current finding, a timely Windows notice, or a cautious forecast; when none stands out, it reports that and shows the latest available CPU/memory sample. If CPU or memory readings are unavailable, it says which measurement it cannot assess instead of implying there is no resource issue. If several informational changes are active, it prioritizes a rapid memory rise, then a shift above the device’s personal baseline, ahead of other informational findings. It also calls out large CPU, GPU, or memory changes between adjacent fresh samples (15 CPU points, 20 GPU points, or 5 memory points), showing before-and-after readings while skipping stale data and long gaps and labeling the change as observation rather than diagnosis. Repeated callouts for each metric have a 30-second cooldown to keep the dashboard calm during a continuing shift. If a sample timestamp is in the future relative to the PC clock, the dashboard flags the mismatch and withholds a live interpretation. When a finding has a confidence rating, the readout also shows the evidence basis; confidence applies to the observed condition, not its cause. For sustained CPU or memory findings, it can add the freshest relevant per-process reading as a possible contributor and mention nearby Windows events when their timestamps overlap. Stale process or event data is not used for that context, and timing or resource association is never presented as proof of cause. This uses data Ausyn already collected, not a new polling loop or an automatic cloud request. The written Assistant remains available for follow-up questions.

The Hardware screen now retains a bounded local timeline of Windows-reported device-profile changes, displays the newest entries, and includes recent changes in system reports. Users can clear the timeline without erasing Ausyn’s current hardware baseline. A recorded change is not treated as proof that hardware caused a later performance shift.

Startup & apps also tracks software inventory changes locally: the first scan creates a baseline, while later refreshes can note an app first observed or a version difference. Ausyn timestamps when it detects the difference, not when the software was installed, and does not infer removals from missing entries. The 100-entry history and its app-name/version baseline can be cleared together; neither is sent to cloud AI.
On recommendation cards, users can record whether trying a step helped, made no change, made things worse, or had an unclear result. Ausyn stores one report per incident locally, labels it as user-reported feedback rather than proof, includes it in history exports, and deletes it when local history is cleared.

CPU and memory pressure recommendations also support an optional before-and-after check. Ausyn saves the current Windows-reported CPU/memory baseline locally, lets the user try the suggestion in their own time, then records a later sample. It displays only the observed changes and explicitly does not claim that the suggestion caused them. The checkpoints are included in history exports and are deleted when local history is cleared.

When a finding recurs, Ausyn can summarize rated reports from earlier incidents with the same rule. It waits for at least five rated reports before showing a percentage, excludes unclear reports from that denominator, and clearly labels the aggregate as self-reported experience rather than causal evidence.

Diagnostic findings include a qualitative confidence label with its basis. For sustained CPU or memory patterns, confidence refers to the repeated observation only; it does not identify a root cause. Direct Windows readings are described as confidence in the reported value, with relevant context about possible impact.

Findings open in a plain-language view with evidence, confidence basis, and first-seen details available per card. Settings can start findings with those details expanded; changing this preference updates both Diagnostics and Recommendations. Assistant answers continue to honor the same technical-detail preference.

Ask Ausyn “How do you know?” to see the current Windows readings, active finding evidence, sample timestamp, and confidence basis. It distinguishes measurements from causal explanations and states when there is no sustained finding to support a diagnosis; cloud requests include minimized relevant evidence under the normal review and privacy controls.
The Assistant page offers editable quick questions for a system check, a slowdown, memory use, the current process list, and a storage outlook. The storage question uses the same local history-backed forecast and states when there is not enough consistent history to estimate a date.

The current build includes the desktop shell, live Windows monitoring for CPU, memory, graphics-engine counters when available, fixed-drive capacity, battery readings, physical network throughput, and a searchable, sortable list of running processes visible to the current account. The Performance process table also shows TCP connection and UDP endpoint counts per listed process where Windows provides owner-PID tables; these counts are not per-app network byte rates. Process details remain in memory and are not written to telemetry history. It stores aggregate history locally, provides charts, a partial measured performance score, evidence-backed diagnostics, and user-led recommendations. Event intelligence reads recent Windows System and Application warnings/errors on demand, groups repeats, and shows formatted event messages locally; the incident replay also lists loaded Windows event groups within 15 minutes of a finding's latest observation. Timing is context, not proof of cause. Startup & apps provides a read-only inventory of common startup registry/folder entries and installed-app registry metadata, with a shortcut to Windows Startup settings for changes. The Assistant can answer offline from local evidence or use an optional OpenAI-compatible cloud endpoint. Cloud AI is off by default; each request shows its minimized context and requires confirmation. Optional OpenAI web search is a separate opt-in, uses `gpt-5-search-api`, may incur API charges, and displays clickable source citations. API keys are protected with Windows DPAPI. Settings include response style, local chat saving (off by default), process-name sharing (off by default), desktop alerts, and 7/30/90-day retention. Closing the main window hides Ausyn in the Windows notification area; **Quit Ausyn** on its tray menu exits completely. History can be exported or cleared. The Predictions page estimates when the Windows or a connected secondary fixed drive could reach 10% free space, only after enough consistent daily history. The Hardware page also shows Windows Storage health status and media type, plus reliability counters when the drive and driver expose them: device temperature and maximum, wear indicator, power-on hours, and uncorrected read/write errors. Ausyn checks them every five minutes; unsupported counters stay unavailable. A Windows Warning/Unhealthy status, reported wear limit, or uncorrected errors can create a cautious dashboard finding, appear in local reports, and be explained by the written Assistant. These drive-health questions stay local even if optional cloud AI is enabled. Findings prompt backup review without asserting imminent failure, and these signals do not alter the partial performance score. Battery wear/lifespan and thermal forecasts remain unavailable; supported devices can show a daily battery-capacity-health trend and a sustained ACPI thermal-zone warning. A sufficiently large two-week capacity-estimate decline can also produce an informational finding, without diagnosing battery condition or predicting replacement. Gaming readiness has publisher-sourced profiles for Fortnite, Cyberpunk 2077, both GTA V editions, Apex Legends, and Counter-Strike 2, detects those games shortly after launch, checks measurable hardware minimums, and can notify about likely pressure. Its Auto mode adapts settings suggestions to recent system-wide CPU/memory/GPU load and available Windows thermal-zone readings; it never edits game settings or promises FPS. CPU/GPU model equivalence remains unscored, so “meets known resource checks” is not a compatibility guarantee. Custom profiles can also be saved locally with source notes. The Battery & power page can inspect Windows sleep blockers on demand and, with confirmation, apply a Windows-enumerated power plan and offer session-only undo after verification.
The Windows sign-in option in Settings is opt-in and current-user-only. When enabled, Ausyn writes its quoted installed executable path to the current account’s standard Windows Run key; it does not create a scheduled task or request administrator access. Disabling the option removes that entry, and uninstalling Ausyn also cleans up its startup entry.

For general storage questions, the Assistant lists all Windows-reported fixed local volumes when more than one is available, while direct drive-letter questions can focus on a specific volume. Volume capacity is kept distinct from aggregate physical-disk throughput, and Ausyn does not inspect files to explain what occupies space.

Low-space diagnostics also cover each reported fixed volume, not only the Windows system drive. Secondary-volume warnings use a stable drive-letter finding ID, apply the same measured 10% warning and 5% critical thresholds, and do not add extra weight to the partial health score.

Separately, Ausyn scans a short recent window of local Windows System and Application logs every five minutes. It surfaces new Critical/Error groups and Warning groups that repeat at least three times, with one combined alert per ten minutes and per-event cooldowns. The event message is evidence, not a diagnosis.

For startup registrations with a single exact executable-path match, Ausyn also watches process use across three process samples. If it remains above 15% CPU or 512 MiB working set, the dashboard can proactively suggest reviewing that entry; optional local notifications are cooldown-limited. This does not prove the startup entry launched the process or caused slow boot, and the transient process name is not saved in history.

Security & updates displays Windows Security Center health for antivirus, firewall, and automatic-update settings, plus restart indicators and an explicit offline scan of the local Windows Update cache. It does not install updates, contact Windows Update for a live scan, or claim a cached empty result proves the device is current. Hardware also includes OS build, native architecture, boot time, uptime, inferred form factor, firmware identity, and physical storage model/bus details where Windows exposes them; storage serial numbers are not collected. Startup & apps can export the currently filtered startup or installed-app list as a UTF-8 CSV to a user-selected location.
The Performance screen includes per-logical-processor load when Windows exposes the relevant performance counters; otherwise, overall CPU use remains available independently.
The persistent status pill shows whether system readings are live, delayed, or still starting. Its stale threshold follows the selected sampling interval. If readings are stale or have not arrived yet, the Assistant explains that it cannot make a live diagnosis and does not send cached readings to cloud AI.
Natural questions such as “Which app is using the most RAM?”, “What is using my CPU?”, and “What’s running?” are routed to the local process breakdown when fresh process readings are available. If a listed process name appears in a resource or slowdown question, Ausyn focuses on that process even when the question does not say “process” or “app.” Process questions stay local and don’t invoke cloud AI. The answer ranks the current sample and clearly says it is not a sustained trend or proof of cause.
Fresh installations sample every five seconds by default as a lower-overhead balance. Settings retain 1-, 2-, 5-, and 10-second choices; faster updates are more responsive, while slower sampling can delay findings and reduce history detail. Existing saved sampling choices are preserved. Optional adaptive low-overhead mode temporarily moves sampling to 10 seconds after six consecutive samples where collection consumes at least 20% of the interval or Ausyn itself uses at least 2% of total system CPU capacity. It restores the selected interval after 12 low-load samples, requiring collection under 8% of the interval and Ausyn below 1% of total CPU capacity. CPU use is measured from Windows process-time counters over monotonic elapsed time; if that reading is unavailable, collection latency still controls adaptation. The mode is enabled by default and can be turned off in Settings. Agent health shows the effective cadence, and the written Assistant can explain the trigger, current interval, and collection-time evidence locally. Ausyn also gives a one-time status-bar notice when adaptive slowing begins or ends.

For a quicker workload heads-up, Ausyn tracks a 30-second rolling window of fresh CPU and memory readings. At balanced sensitivity, after at least 20 seconds it adds a briefing when CPU averages at least 75%, memory at least 85%, or both CPU (60%) and memory (78%) are elevated together. Memory staying at or above 95% across repeated fresh readings spanning at least five seconds creates an earlier warning; at 97% or higher with at most 256 MiB available it is critical. The rule supports 2-, 5- and 10-second sampling and rejects missing/invalid readings and large gaps. Advice includes available headroom, fresh process context when available, and safe next steps. Ausyn cards are the default desktop channel; the Windows channel remains optional. Repeats about the same resource are spaced out, while escalation can interrupt. Quiet hours and category switches still apply. The dashboard and logs report observations and recovery without claiming an app caused the load or that Ausyn changed the PC.
If local history storage temporarily fails, live monitoring continues and Ausyn keeps only compact history fields in a bounded in-memory queue. It retries storage and writes buffered samples oldest-first when the database recovers. The queue holds up to 180 scheduled samples (about 30 minutes); closing Ausyn before recovery or a longer outage can leave a gap in saved history.
Agent health also reports Ausyn's own process CPU share, working set, and private memory alongside collection latency. It summarizes recent working-set and private-memory averages and peaks as well as the latest readings. A lightweight chart shows up to 60 recent CPU-use and working-set samples in separate scales; the footprint is sampled during the existing telemetry refresh and is not written to history.
The process table includes Windows process I/O read/write byte rates. They are not guaranteed physical-disk throughput, and process-level history is not retained.
Startup & apps now compares configured startup commands with the live process list and shows current usage for a possible match. Path/name matches do not prove that the startup entry launched the process or caused performance impact; this correlation stays local and is not persisted.
An exact executable-path match receives a review suggestion only after CPU remains at or above 15% or working set at or above 512 MiB for three consecutive process samples. This is a local heuristic, not a claim about boot impact.
When a process is selected, Ausyn keeps up to 30 recent CPU, working-set, and read/write I/O samples in memory for a temporary trend. The chart scales each metric independently and leaves unavailable readings out of that metric’s line. A companion profile reports average/peak process readings and how often a large working set coincided with high system memory in the same samples; this is a workload association, not cause attribution. The samples are cleared on selection change or when the app closes.
Selecting a process shows current readings and its executable path when accessible. Process details remain in memory and are not written to telemetry history; per-process history is not retained, so historical trends are unavailable.
Data quality shows the source and validation state of current readings. Impossible values are excluded before analysis and history storage, while valid unusual values are kept; Windows-provided battery runtime is marked as an estimate.

## Build on Windows

Requirements:

- Visual Studio 2022 Build Tools with the **Desktop development with C++** workload and a Windows 10/11 SDK.
- CMake 3.24 or newer.
- Qt 6 for MSVC 2022 x64, including Qt Widgets.

Set `QTDIR` to the installed MSVC Qt kit root, for example, then run the helper from PowerShell:

```powershell
$env:QTDIR = 'C:\Qt\6.11.2\msvc2022_64'
.\scripts\build.ps1
```

The helper locates the installed Visual Studio C++ toolchain, initializes its developer environment, and runs CMake with the matching Qt kit. No global `PATH` edits are needed. You can also use the included CMake preset from a regular, correctly initialized Visual Studio developer shell.

To create a portable Windows x64 release ZIP with Qt and compiler runtime files included, run `.\scripts\package.ps1` in PowerShell. Extract the ZIP and start `ausyn.exe`; users do not need Qt or the source project installed. The release helper checks that the core Qt and SQLite plugin files are present before producing the ZIP.

When Inno Setup 6 is installed (or `INNO_SETUP_COMPILER` points to `ISCC.exe`), the package script also builds a Windows installer with Start Menu and optional desktop shortcuts. It requests administrator approval to install under Program Files. Uninstalling Ausyn leaves the user's settings and local history intact.

## Product principles

- Explain observations with evidence and make uncertainty visible.
- Treat missing or unsupported sensors as unavailable, never as zero.
- Keep telemetry local by default and let the user control any AI connection.
- Require a clear preview and user approval before a system-changing action.
- Keep everyday screens approachable while making technical detail available on demand.

## Assistant and local data

Assistant answers are generated from live values and active findings already collected by Ausyn. It explains CPU, memory, graphics, battery, storage, and the partial performance score. It marks unavailable sensors plainly and avoids claiming that a reading proves the cause of a problem. Cloud answers are optional, disabled by default, and require both a saved provider credential and an explicit per-request review. See [the AI privacy notes](docs/ai_privacy.md) for the transmitted context and safeguards.

For slowdown questions, the local Assistant combines live CPU, memory, GPU, disk-transfer, and network-transfer readings with sustained findings from local history. It ranks the active evidence into possible contributors, gives a next step, and distinguishes repeated pressure from a one-sample spike. Disk throughput is not disk latency, network traffic is not connection quality, and fresh process samples remain context rather than proof of cause. When no monitored pattern stands out, Ausyn explains what its measurements cannot rule out instead of inventing a diagnosis.

The local Assistant can answer direct questions about the processes currently using the most CPU or memory, and show process I/O rates or TCP/UDP endpoint counts when Windows exposes them. These are short-lived process samples; they do not prove a cause and are not stored as process history. Per-process network bandwidth is not collected, and process I/O counters are not guaranteed physical-disk throughput.

For questions about background load, Ausyn can compare the current foreground process with other sampled processes and summarize their readable CPU and memory use. This foreground app name is transient local context, is not saved to history, and is not sent to cloud AI. The comparison is a recent snapshot rather than proof that background activity caused a problem.

Questions about performance history, averages, peaks, or trends are answered from locally saved samples. Ausyn weights stored aggregates by their represented sample count, compares early and recent portions only when enough points are available, and labels the result as a sampled direction rather than a prediction. Saved-history questions stay local even when optional cloud AI is enabled.

History & reports can create a full local SQLite backup and restore one after Ausyn checks its integrity, schema version, and required tables. Restore preserves the current database while replacing it and attempts to roll back automatically if the replacement cannot be opened. Backups include performance history and findings, but not settings or saved conversations; store a copy away from the PC for protection against device loss.

Ask whether current CPU or memory use is normal, usual, or typical to compare the fresh readings with this PC’s own saved averages for the selected history window. Ausyn requires at least five saved points and samples, reports the coverage and time span, and labels this as a personal comparison rather than a health standard. The request stays local and requires fresh telemetry.

The Assistant can also explain Ausyn’s system-drive and connected secondary-drive storage outlooks, including a requested drive letter or volume label, its short-term memory-pressure outlook, and its battery outlook. Storage estimates project the observed trend to the 10% free-space attention threshold; the memory outlook estimates reaching 90% average use only when recent five-minute windows show a fresh, well-sampled, consistent rise; battery outlook estimates reaching 15% charge only while discharging. These evidence questions use local data even when cloud AI is enabled. Ausyn does not diagnose a memory leak, forecast battery wear, or claim an estimate predicts shutdown or a certain future date.

The Predictions page charts memory and battery readings alongside their attention thresholds. Dashed projections appear only when the corresponding local trend meets its evidence requirements; battery history is sampled evenly to at most 60 plotted readings. Forecast cards expose their current evidence state, and chart summaries include key values for assistive technology.

Ausyn also surfaces a proactive “heads-up” on the dashboard without requiring a chat question. It prioritizes active sustained findings and includes system-drive and secondary-drive storage forecasts within 90 days, plus battery forecasts within two hours, when those estimates are available. Optional Windows notifications trigger once when a forecast first enters a nearer 30-day storage or two-hour battery window; secondary-drive alerts also cover sharp daily space drops. A current low-space finding suppresses the matching system-drive forecast alert. Settings provide a global notification switch, individual controls for findings, forecasts, event logs, startup items, and security/restart signals, plus a daily quiet-hours window that supports overnight ranges. Quiet hours pause desktop notifications while dashboard findings continue to update. Forecasts are conditional estimates, not guarantees.

Security & updates status is also refreshed locally every five minutes. A newly reported Windows Security Center warning or pending-restart indicator appears in the proactive dashboard card and can trigger a one-time Windows notification until that state clears. Ausyn reports the status Windows provides; it does not change protection settings or restart the PC.

After at least one hour of saved samples, Ausyn also compares the latest five-minute CPU and memory averages with this PC’s preceding 24-hour baseline. A substantial increase appears as an informational heads-up with the measurements and a review suggestion. It does not label expected workloads as faults, infer what the user intended to do, or automatically close processes. Baseline queries are refreshed every five minutes to keep monitoring overhead low.

Ausyn also compares adjacent five-minute memory averages. If the latest average reaches at least 75%, is at least 12 percentage points above the preceding window, and remains below the existing sustained-pressure threshold, it creates a short-lived informational heads-up. This detects a fast change before the high-pressure rule without diagnosing a leak; the prior-window comparison reuses the existing local history store.

The Predictions page also fits a short-term memory trend from well-sampled five-minute history windows. It requires at least five windows spanning 20 minutes, fresh samples, no large gaps, a linear-fit quality of at least 65%, and a confirmed rise in three of the latest four windows. A median pairwise slope reduces the influence of one unusual window; Ausyn withholds estimates beyond two hours. The dashboard calls out estimates within an hour, and optional notifications alert once when the threshold is projected within 30 minutes. This is a workload-sensitive trend estimate, not a memory-leak or process diagnosis.

When desktop notifications are enabled, a newly detected personal-baseline shift can also appear as one Windows notification for that episode. A 30-minute per-finding cooldown prevents repeated alerts if the measurement briefly clears and returns. It is informational and explicitly distinguishes a change from a fault.

For a fresh baseline-shift heads-up, the dashboard may add the highest current CPU process or largest working set as transient context. It labels these as associations only; process details are not added to saved findings or sent to cloud AI as part of the proactive card.

Health-score questions include the measured component scores, their weights, evidence, and coverage. The Assistant identifies the score as a partial performance-and-storage index; missing thermal, battery, security, and update signals are not silently treated as healthy.

Ask “What are my PC specs?” for a natural-language hardware summary based on the device, CPU, graphics, memory, storage, Windows, and battery details currently exposed by Windows. Optional cloud requests include those matching facts in the review preview; unavailable fields remain clearly unavailable.

For recent Windows reports, ask Ausyn about application crashes, blue screens, disk errors, or Storport events. It summarizes readable local event records and their recurrence without claiming that a log entry proves the cause.

Requests such as “Make my laptop perform better” use the current sustained findings to suggest user-controlled next steps. Ausyn explains the supporting evidence, a possible benefit, and practical risks; when no monitored issue supports a change, it asks for the situation instead of proposing generic tweaks. The optional cloud context includes the same current findings and suggestions.

“Check my system” and “Scan my laptop” produce a local quick check of fresh CPU, memory, GPU, every reported fixed drive’s current free space, network, available battery and thermal readings, plus active findings and the partial score. This is not a malware scan or exhaustive hardware test; Ausyn does not inspect file contents. Full-system-check questions stay local and require fresh telemetry.

Questions such as “Can I play this game?” use the current Gaming readiness profile. Ausyn reports the entered RAM, dedicated VRAM, and install-drive checks, and stays clear that this is not a game catalog, CPU compatibility check, anti-cheat check, FPS estimate, or launch guarantee. Game-readiness answers stay local.

Ask “Prepare my laptop for gaming” for a local review of the current game profile and sustained CPU, memory, or system-drive findings. Ausyn suggests only user-controlled next steps supported by those findings, never closes apps, and labels live CPU/memory readings as momentary. Preparation questions require fresh telemetry and stay local.

The Gaming readiness page also has a user-triggered pre-game scan. It checks fresh CPU, graphics, and memory readings; Windows-reported AC power; the highest available ACPI thermal-zone reading; the selected drive against an entered storage requirement; and up to three current top memory users. Stale process samples are called out. This is a point-in-time checklist: high utilization is not diagnosed as a fault, ACPI zones may not reflect CPU/GPU die temperature, and Ausyn does not close apps or change settings.

Ausyn's written Assistant uses whole-word intent matching so ordinary words such as “which” or “program” are not mistaken for short keywords. It handles greetings, thanks, farewells, and capability questions directly. Optional cloud replies are prompted to sound natural and concise while remaining clear about what the evidence can and cannot establish. Chat history is not sent to the provider.


Conversation history is not saved unless the user enables it in Settings. When enabled, the most recent 100 chat messages are stored in the app's local data directory. Telemetry and findings remain in the local SQLite database and can be exported as CSV or deleted from History & reports. Retention is configurable from 7 to 90 days.

The creator easter egg is revealed after seven clicks on the Ausyn mark. The written Assistant also answers explicit questions about Ausyn's creator or lore; incidental mentions of the supplied names do not trigger the easter-egg answer. Personal details are not shown in the ordinary interface.

The Assistant can summarize the latest readable System and Application event-log signals when asked about Windows errors, application crashes/hangs, blue screens, or unexpected shutdowns. Ausyn highlights Kernel-Power event 41 and EventLog event 6008 as unexpected-shutdown signals, System event 1001 as a bugcheck/blue-screen restart, and Application event 1002 as an app that stopped responding. Event intelligence labels each row by signal type so users do not have to decode event IDs first. Ausyn clearly states that these records do not identify the cause or faulty hardware. Answers stay local, use the existing on-demand event scan, show event provider, ID, severity, recurrence count, and timestamp, and distinguish recorded evidence from a diagnosis. Formatted event messages and other log channels remain available on Event intelligence.

For a slowdown question, the Assistant can also surface a Windows event recorded within two minutes of the start of a sustained CPU or memory finding. This nearby timing is a local-only clue, explicitly labeled as correlation rather than cause; it does not change the finding’s diagnosis or confidence.

On first launch, Ausyn explains its local monitoring and privacy defaults before the user continues. The guide can be reopened from Settings; it does not request elevated permissions or enable cloud AI.

History & reports can summarize locally recorded CPU and memory averages and highest recorded samples across 24 hours, 7 days, or 30 days. Its five-part system report can be exported as paginated PDF or HTML. It includes a health overview with scored-component evidence, a current Windows-reported system snapshot with data-quality notes and next steps, active findings with evidence and suggested review steps plus nearby event timings from a recent on-demand scan, storage outlooks, and battery outlook/capacity history when available. The history summary reports the actual first-to-last sample window and elapsed time within the selected period, alongside sample counts and averages, so the selected range is not mistaken for continuous coverage. The snapshot records when its readings were captured and flags samples that may be out of date. The PDF has page numbers. Event timing is labeled as correlation, not cause. Missing Windows readings are labeled as unavailable. Before saving, users choose a privacy-friendly report that omits processor/graphics models, the exact Windows build, drive labels and paths, and hardware-change entries, or a full-detail report. Both versions exclude chat history and per-process names/readings; exporting stays local until the user chooses to share the saved file. Longer history periods use five-minute database aggregates; the CSV export remains available for detailed local history data.

## Predictions and game requirements

Storage forecasting aggregates local samples by day. A forecast requires at least five daily points spanning four days, fresh history, consistent drive capacity, a linear-fit quality of at least 65%, and a decline in at least two of the latest three daily changes. The rate uses the median pairwise slope to reduce sensitivity to one unusual day. The estimate projects daily free-space percentage to the existing 10% attention threshold. The UI shows observation length, robust trend rate, recent-direction check, fit, and confidence. It does not claim a certain date.

The local history schema also retains timestamped capacity samples for every detected fixed volume, keyed by its drive root. Per-drive records are sampled at five-minute intervals to keep local database growth low; any due drive sample is committed atomically with its telemetry snapshot. These samples share the configured retention period, are removed by Clear History, and are included in CSV exports as `volume_sample` rows with a `volume_root_path`. The Prediction page uses daily averages to estimate trends for connected secondary fixed drives as well as the Windows drive, with a compact per-drive chart; disconnected drives are not shown as available. Each drive needs sufficient fresh, consistent history before Ausyn provides a depletion estimate.

The storage outlook separately flags a sharp change when the newest daily sample is at least 5 percentage points below the previous sample, 18–36 hours earlier. It suppresses a linear depletion estimate for that pair and surfaces a dashboard heads-up plus an optional one-time notification. This is a measured daily-average change; Ausyn cannot attribute it to a process or identify files to remove.

The Gaming readiness screen compares measurable minimum resources with publisher values and includes a small built-in source-dated catalog (Fortnite, Cyberpunk 2077, GTA V Enhanced, GTA V Legacy, Apex Legends, Counter-Strike 2), plus user-saved local profiles. A saved profile may include a validated `.exe` filename so Ausyn can recognize that process too; it does not inspect executable contents and detections can be confused by a shared executable name. Ausyn detects matching names at its existing process-sample interval and reports shortly after game launch; it cannot intercept or block a launch before Windows starts the process. It reports below-minimum resources, current system pressure, and available thermal-zone evidence with uncertainty. Its Auto mode uses recent whole-system CPU, memory, graphics-engine, and reported thermal headroom to recommend game-setting adjustments; preset labels and advice are suggestions, not predicted FPS or measured in-game performance. It does not edit configuration files or apply settings. Exact CPU/GPU model equivalence, game resolution, drivers, and title-specific frame rate are not inferred. Gaming sessions remain in-memory summaries and are not saved to history. Battery & power provides an on-demand read-only Windows sleep blocker check and a user-confirmed switch among available power plans with active-session undo and verification.

For a built-in game or a saved custom profile, **Check & launch game** gives an explicit pre-launch readiness summary. It calls out below-minimum resources, incomplete checks, stale readings, and high current system load, then requires a separate **Launch anyway** choice before starting when those warning conditions apply. Ausyn launches only the chosen executable and leaves its arguments empty. Games that require their original store launcher or anti-cheat should still be started from that launcher.
