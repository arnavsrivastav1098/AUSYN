# Windows monitoring sources

Ausyn samples on a background Qt thread so that Windows calls and process enumeration do not block the interface. System telemetry follows the selected interval (five seconds by default for fresh profiles). Process snapshots are considered on each telemetry pass and refreshed no more often than every five seconds; when telemetry is set slower, process data updates at that slower cadence too.

| Reading | Source | Meaning and limits |
| --- | --- | --- |
| Processor use | `GetSystemTimes` deltas | Total system busy time across the sample interval. The first sample establishes a baseline. |
| Per-core processor use | PDH `Processor Information(*)\% Processor Time` | Per-logical-processor Windows counters, when available. The first or invalid counter interval is shown as warming up/unavailable; the aggregate `GetSystemTimes` reading remains independent. |
| Physical memory and available memory | `GlobalMemoryStatusEx` | Windows-reported physical total, in-use amount, and immediately available amount. Available memory is distinct from cache. |
| System cache | `GetPerformanceInfo` (Psapi) | Windows-reported cache size. Cached pages are reclaimable and are not equivalent to free memory; the reading may be unavailable on some systems. |
| Graphics adapters and dedicated memory | DXGI adapter enumeration | Hardware adapters are enumerated and labeled separately. Gaming readiness still uses the first adapter for comparison. Dedicated VRAM is reported from the adapter descriptor; it may be zero for integrated GPUs. |
| GPU local-memory usage | `IDXGIAdapter3::QueryVideoMemoryInfo` | Current adapter usage and Windows’ dynamic budget when supported. The budget is not physical VRAM capacity and can change with system load. |
| Graphics use | English PDH `GPU Engine` counters | Highest reported engine percentage. This is explicitly an engine reading, not a sum or a promise of total GPU utilization. It is unavailable when Windows exposes no matching counters. |
| Fixed-drive space | `GetDiskFreeSpaceExW` | Capacity and user-available free space for fixed drives; the dashboard highlights the Windows system volume. |
| Physical-disk throughput | PDH `PhysicalDisk(_Total)` read/write byte-rate counters | Aggregate bytes per second across all physical disks. This is throughput, not per-drive utilization or a diagnosis of drive health; the first interval may be unavailable. |
| Battery charge and AC state | `GetSystemPowerStatus` | Current charge percentage and charging/AC indicators where the device reports a battery. Battery health and cycle counts are not inferred from charge percentage. |
| Battery rate, capacity, and runtime estimate | `CallNtPowerInformation(SystemBatteryState)` | Windows-reported remaining/maximum capacity, signed rate, and estimated seconds when supported. These do not expose battery design health, so Ausyn does not calculate a wear score. |
| Physical-drive status and reliability | Windows Storage WMI provider (`MSFT_PhysicalDisk`, `MSFT_StorageReliabilityCounter`) | Queried every five minutes when successful; a failed read is retried after about 30 seconds. Ausyn reports provider health state and media type, plus only reliability fields the provider/drive returns (temperature, reported maximum, wear indicator, power-on hours, and uncorrected read/write errors). Unsupported or inaccessible data remains unavailable; these device-reported values do not certify a drive or predict a failure date. |
| Thermal-zone temperatures and firmware trip points | `MSAcpi_ThermalZoneTemperature` in `ROOT\\WMI` | Current values and passive/critical points are normalized from tenths of kelvin when provided. Ausyn tracks time at/above a zone's reported passive point in memory; zone identity/thresholds may be inaccurate and are not generalized to CPU/GPU component limits. |
| Fan activity and requested speed | `Win32_Fan` in `ROOT\\CIMV2` | Windows may expose active-cooling state and a requested speed target. `DesiredSpeed` is not itself measured rotor RPM; telemetry is absent on many devices. Speed-target changes can be compared with CPU load and ACPI-zone readings, but Ausyn does not diagnose a physical fan fault from these signals alone. |
| Battery design and full-charge capacity | `ROOT\\WMI` `BatteryStaticData` + `BatteryFullChargedCapacity` | When matched battery tags and absolute capacity units are exposed, Ausyn estimates full-charge/design capacity as a percentage. Firmware/driver reporting varies; this is an estimate, not a battery diagnosis, and can exceed 100%. |
| Network rates | `GetIfTable2` counters | Byte-rate deltas across active hardware interfaces. Loopback, tunnel, and non-hardware interfaces are excluded. The first interval establishes a baseline. |
| Active network adapters and connection counts | `GetIfTable2`, `GetExtendedTcpTable`, `GetExtendedUdpTable` | Lists active physical adapters and aggregate IPv4/IPv6 TCP rows (including listeners) and UDP endpoints. Owner-PID tables attribute endpoint counts to listed processes when Windows provides them. These are connection counts, not per-process byte rates. Remote addresses are read only after the user explicitly selects a process and requests endpoint inspection; only TCP remote endpoints and UDP local endpoints are shown, and they are neither persisted nor sent to cloud AI. Packet contents are never collected. |
| Local gateway latency and echo response | On-demand Windows ICMP echo to the selected IPv4 default route | Five small probes run only after the user clicks Check local gateway. Reports round-trip time and echo non-responses; an ICMP-filtering gateway may not reply, so missing replies are not claimed as general packet loss. This is local gateway latency, not Internet latency. |
| Secure endpoint reachability | User-triggered Qt DNS lookup and `QSslSocket` TLS handshake | Checks the host the user enters on TCP port 443 with peer verification enabled. Reports DNS and connection setup timing and the resolved address. Ausyn sends no HTTP/page request or application content, and keeps no result history. DNS lookup runs in a worker so a slow resolver does not block the UI; connection setup has an eight-second timeout. This checks reachability to one chosen endpoint, not general Internet quality or availability. |
| Process CPU, memory, I/O rates, and executable path | Toolhelp process snapshot, PSAPI working set, `GetProcessTimes`, `GetProcessIoCounters`, `QueryFullProcessImageNameW` | All processes visible to the current account are listed. Snapshot collection runs when a telemetry pass occurs and at least five seconds have elapsed; a slower telemetry setting also slows process refresh. The Performance page shows the process snapshot age and refresh target so cached rows are distinguishable from the latest system sample. If Windows cannot finish enumeration, Ausyn retains the last successful process list and timestamp, reports the collection failure, and avoids replacing valid process baselines. The assistant calls out a failed refresh and declines to use an over-age sample. I/O read/write byte rates are deltas of Windows process transfer counters; they are not guaranteed physical-disk throughput. The table supports local search and column sorting; selecting a row shows the sample age and executable path when accessible. Up to 30 recent CPU, working-set, and read/write I/O samples for the selected process are held in memory only and cleared when the selection changes or Ausyn closes. The chart scales these metrics independently and keeps unavailable values out of the affected line. No per-process history is persisted. Access restrictions are represented as unavailable; the monitor does not request administrator access. |

The Overview and Performance views continue to show the busiest GPU engine counter exposed by Windows; it is not a sum of all adapters. Adapter memory usage/budget is displayed separately from fixed dedicated VRAM capacity.

## Event intelligence

The Event intelligence screen queries the local Windows `System` and `Application` channels, plus `Microsoft-Windows-Storage-Storport/Operational` when available, for Critical, Error, and Warning records from the last 24 hours. Each channel is capped at 500 returned events per refresh. Repeated events are grouped by channel, provider, and event ID, with the occurrence count, first and most recent timestamps, and a formatted publisher message when Windows has the provider metadata available. Selecting a repeated group shows its observed time span as descriptive timing only, not proof that the events share a cause. It also lists up to four other groups whose most recent records occurred within two minutes, labeled as nearby co-occurrences rather than causal correlations. Search and severity filters run locally in the UI. Messages are presented as evidence and are not used to claim a root cause. If Windows denies access to a channel, readable channels remain useful and the limitation is shown. Users can export the currently visible filtered event groups as UTF-8 CSV; before saving, Ausyn warns that Windows messages may include paths, account names, or device details. The export is created locally at the chosen location and is not uploaded by Ausyn. A button can open Windows Reliability Monitor (`perfmon.exe /rel`) for a separate native stability timeline; Ausyn makes no changes to Windows. Event messages are not persisted or sent to the optional AI provider.

Ausyn identifies System event 41 from `Microsoft-Windows-Kernel-Power` and event 6008 from `EventLog` as unexpected-shutdown signals. It separately classifies System event 1001 from `Microsoft-Windows-WER-SystemErrorReporting` as a bugcheck/blue-screen restart, and Application event 1002 from `Application Hang` as an application that stopped responding. These signals are highlighted in Event intelligence, the proactive briefing, and local Assistant responses. Windows may record unexpected-shutdown events after power loss, a crash, or a forced shutdown; bugcheck events may include a stop code in their formatted message. None of these signals identifies a faulty component or establishes a cause. Events remain grouped by their original provider and ID, so duplicate records are not combined into an invented single incident.

System events from `Microsoft-Windows-WHEA-Logger` are labeled as Windows Hardware Error Architecture reports in Event intelligence, local Assistant summaries, and qualifying proactive notices. Ausyn preserves Windows severity and the formatted message, asks users to review recurrence, and does not infer that a report identifies a faulty component or proves hardware failure.

Records from Microsoft's `Microsoft-Windows-Storage-Storport` provider are labeled as storage-driver events in the System channel and the Storport Operational channel. These records may reflect device failures, telemetry, debugging, or optimization; Ausyn preserves Windows severity and message and does not treat the provider label alone as proof of a failing drive. The provider and Operational-channel naming follows Microsoft's [Storport event-log documentation](https://learn.microsoft.com/en-us/windows-hardware/drivers/storage/storport-event-log-extensions).

Application Error event 1000 records expose Windows' named `AppName`, `ModuleName`, and `ExceptionCode` fields when present. Event intelligence shows these fields as reported diagnostic clues, and local Assistant summaries can include them. When `AppName` is present, repeat crash records are grouped and alerted per application so unrelated apps are not combined into one count or allowed to suppress each other's notice; records without that field retain the provider-and-event grouping. Missing or unnamed data remains unavailable; Ausyn does not infer a cause from the module or code.

In the background, Ausyn checks only the last ten minutes of local System, Application, and available Storport Operational events every five minutes, capped at 100 per channel. Publisher messages are formatted only for Application Error Event ID 1000, so the proactive summary can name the faulting application when Windows provides that field. This exact Application-channel/provider/ID combination is identified as an application crash report; Ausyn does not infer its root cause, and other event groups remain generic evidence. New Critical/Error groups and Warning groups with at least three occurrences appear in the proactive dashboard card. Optional notifications are rate-limited to one combined event alert per ten minutes and once per event group per 30 minutes. This short-window summary is transient and local; an initial scan seeds the current state without notifying old events. Application names are not persisted or sent to the optional AI provider.

Clicking an Ausyn Windows notification opens the screen for the most recently sent notification category: Diagnostics, Predictions, Event intelligence, Startup & apps, or Security & updates. The alert remains evidence for review; opening a page does not perform a system action.

## Startup and installed-app inventory

The Startup & apps screen reads the current-user and all-user Run/RunOnce registry locations in both 32-bit and 64-bit views, plus the standard current-user and all-user Startup folders. It also reads installed-app display metadata from the corresponding uninstall registry locations. The inventory is read-only: Ausyn does not launch entries, inspect application data, infer whether Windows will delay or block an entry, or change the registry. Startup controls are handed off to Windows Settings. Raw inventory rows and startup records stay in memory and are not written to telemetry history or sent to the AI provider. For change awareness, Ausyn keeps a bounded local baseline of installed-app name/publisher/version/scope identifiers and a 100-entry observation timeline in its per-user settings store; this software inventory is not sent to the AI provider.

The first successful scan establishes a baseline without producing a bulk change report. Later scans can record an app first observed or a version difference, timestamped when Ausyn saw it. Detection time is not install time. Ausyn does not infer uninstallations because a missing registry entry can reflect a partial or inaccessible scan. Users can clear the timeline and baseline together; the next scan starts a fresh baseline.

Startup entries are compared with the current process snapshot using an exact executable path when available, otherwise an executable-name match. Name matches are explicitly marked as possible; even an exact path match cannot prove that the startup registration launched the running process. A missing match is not evidence that an application is stopped. Current CPU and working-set readings are shown when one process matches. Ausyn shows a user-led review suggestion only after a single exact-path match stays above 15% CPU or 512 MiB working set across three consecutive process samples. This threshold is a review heuristic, not a claim about boot impact or causation. Process and startup data remain local and are not persisted together; the brief counter is reset when the inventory is refreshed and is never saved to disk.

When that exact-path startup match sustains the review threshold, Ausyn also surfaces it on the proactive dashboard and can send one local notification for the episode. A 30-minute per-entry cooldown applies if the signal clears and returns. Process names and usage remain transient and are not written into telemetry history.

## Security and updates

The Security & updates screen reads aggregate antivirus, firewall, and automatic-update health from Windows Security Center, plus Windows servicing restart indicators. A lightweight local status refresh runs every five minutes; newly observed `Needs attention` or restart-required states are surfaced on the proactive dashboard and notified once until they clear. This does not identify or certify a specific security product. Update scanning is an explicit user action and queries the local Windows Update Agent cache with online search disabled; an empty cache result is not presented as proof that Windows is up to date. Ausyn never installs updates or changes protection settings. The user can open Windows Settings to manage or check updates directly.

## Hardware inventory

The Hardware screen displays firmware-reported manufacturer/model/BIOS fields and physical storage device model, vendor, firmware revision, and bus where the Windows storage descriptors permit the query. Volume-to-disk mapping is reported when available. Storage serial numbers are not queried. Firmware fields may be empty or generic, and storage mapping can be unavailable on virtual, layered, or access-restricted devices. OS details include the product name, kernel version/build, native processor architecture, estimated last boot, and uptime. Device form factor is a transparent heuristic: battery presence suggests a portable PC; firmware identity can suggest a virtual machine; otherwise desktop/workstation is only a best-effort label. Ausyn stores a compact local baseline of processor, graphics adapter, installed memory, storage model inventory, Windows version/build, and firmware profile. When a non-empty value changes, the Hardware screen reports the old and new values and updates the baseline. This profile stays in Ausyn’s local settings store and is not sent to cloud AI.

Detected profile changes are also kept as a bounded local timeline of up to 100 entries, with the newest 12 shown on Hardware and the newest five included in system reports. Clearing the timeline does not erase the current profile baseline. Entries document Windows-reported identity changes only; their timing does not establish that a component change caused a performance change.

## Telemetry validation and quality

Every live snapshot is validated before it is emitted to the UI, analyzed, or saved. Percentages must be finite and within 0–100; memory used cannot exceed total; free space cannot exceed volume capacity; battery charge cannot exceed 100%; and transfer rates must be finite and non-negative within a generous sanity bound. Invalid readings are removed from analysis and labeled with their observed value and source in Data quality. Valid unusual readings are retained. Windows battery runtime is labeled estimated; unavailable values remain unavailable instead of becoming zero. The quality screen is a current-sample view; it explains each reading's state and offers a state- and sensor-specific next step, while making clear that an unsupported optional sensor is not by itself a device fault. Only the existing normalized aggregate measurements are persisted.

The persistent top-bar monitor status is driven by the timestamp of the latest validated snapshot. It changes from startup to live, and then to delayed when the sample exceeds three selected sampling intervals (with a ten-second minimum). The Assistant will not present cached telemetry as a live diagnosis or include it in a cloud request while that status is delayed. History remains available during collection interruptions.

Fresh user profiles default to a five-second telemetry interval to reduce background sampling work while retaining adequate density for the five-minute analysis windows. Settings still offer 1, 2, 5, and 10 seconds; existing persisted values are preserved. Increasing the interval makes readings less immediate and reduces history detail.

Adaptive low-overhead mode is enabled by default and can be disabled in Settings. It compares measured system-collection duration with the effective sampling interval. Six consecutive passes using at least 20% of that interval temporarily raise the cadence to 10 seconds; 12 consecutive passes using no more than 8% restore the user-selected interval. Intermediate samples reset both streaks to avoid flapping. The current state and effective cadence are shown on Agent health. This safeguard changes only Ausyn's sampling cadence; it does not pause collection, disable alerts, or change Windows settings. A slower cadence can delay updates and reduce history detail.

When the user asks about Ausyn's monitoring cadence, adaptive mode, or collection overhead, the written Assistant answers from the latest local snapshot. It reports collection-pass duration relative to the effective interval and explains the configured thresholds. That duration excludes the rest of the application and must not be read as total Ausyn CPU cost. State transitions also produce a transient status-bar message; no repeated desktop alert is generated.

The Agent health page reports the elapsed duration of each system-collection pass and a rolling average/peak over the latest 60 samples. It also samples Ausyn's own process CPU share, working set, and private memory during the existing telemetry refresh; the page summarizes recent average and peak memory use, and keeps up to 60 CPU/working-set points in memory only. It does not add a separate polling loop or save these process-footprint samples to history. Its delayed state uses the same threshold as the top-bar status: three selected sampling intervals with a ten-second minimum. Assistant answers that use process data apply this same freshness limit to the process snapshot too. Collection timing excludes UI rendering and database work; it is a diagnostic, not a benchmark of total CPU or memory overhead.

Proactive resource-change heads-ups compare five-minute CPU/memory averages with the previous 24 hours, excluding the current five-minute window. Ausyn requires at least 360 stored baseline samples and 24 recent samples, and reports a shift only when CPU is at least 35% and 25 percentage points above its baseline, or memory is at least 75% and 15 points above baseline. Existing sustained-pressure findings take priority when their 90% threshold is reached. The baseline query refreshes every five minutes; a detected shift is informational and does not establish a cause or an unwanted workload.

If SQLite initialization or a scheduled history write fails, the monitor keeps running. Ausyn retries the local database and buffers only the normalized history fields in memory, at the normal ten-second persistence cadence. On recovery it writes samples oldest-first before resuming the current sample. The queue is capped at 180 samples (about 30 minutes); it drops the oldest entries if full and is lost if Ausyn exits before recovery. This protects live monitoring from a history failure without claiming that an outage leaves a complete record.

## Deliberately unavailable readings

Ausyn optionally reads Windows `MSAcpi_ThermalZoneTemperature` values from `ROOT\\WMI`, refreshes the query every ten seconds, and normalizes tenths of kelvin to Celsius. These ACPI zones are not guaranteed to represent CPU/GPU die temperatures. Values outside a broad physical sanity range are rejected, while unusual plausible readings are retained. If Windows exposes no zones, the UI and assistant say so. Vendor-specific CPU/GPU sensors remain unsupported; these live readings are not added to the historical database.

When a zone stays at or above its own firmware-reported passive trip point for at least two minutes, the findings engine surfaces one sustained thermal-zone warning; if the same zone also reaches its reported critical point, the finding is critical. The finding names the reported zone, reading, and threshold, and explains that this is not a CPU/GPU-specific temperature. If Windows notifications are enabled, the first alert includes the observed reading and recommendation; repeat thermal alerts have a 30-minute cooldown, while escalation to Critical is immediate. Ausyn does not change fan controls, throttle applications, or power off the device.

Live readings remain in memory except for a minimized metric snapshot written every ten seconds to a local SQLite database. The database contains time, CPU/memory/GPU readings, system-drive capacity, battery charge, the Windows-derived full-charge/design-capacity estimate when available, and network rates. Connected fixed-volume capacity history is written separately at most once every five minutes per drive, which is sufficient for daily forecasts and bounds history growth. A due volume sample is committed in the same transaction as its telemetry snapshot. The battery estimate is retained only for a local daily trend; it is not sent to an AI provider. Process names and per-process readings are kept in memory for the Performance screen and are not written to history.

History is kept under the current Windows user's local application data folder and pruned to the configured retention period at startup, when the setting changes, and daily while Ausyn is running. Each retention pass removes expired telemetry, resolved findings, and volume samples in one SQLite transaction, so a database error cannot leave only part of those related tables pruned. Active findings are retained until resolved. No telemetry is sent to a network service. History can be cleared or exported from History & reports.
